# 控件树：方案的核心（以及一个容易踩的坑）

AppBridge 高效的关键，是**直接读取 iOS 的无障碍控件树**（Accessibility Tree）做结构化提取，而不是退化为"截图 + OCR"。

## 控件树 vs 截图 OCR

| 维度 | 截图 + OCR（兜底） | 控件树直读（首选） |
|---|---|---|
| 精度 | 依赖视觉模型，可能认错字/漏字 | **精确**：文本、类型、坐标都是结构化的 |
| 速度 | 截图 + 调模型，几秒/页 | **毫秒级**，一次 HTTP 拿整棵树 |
| 成本 | 每次花视觉模型 token | **零模型成本**，纯本地解析 |
| 交互 | 只能"看到"，难定位点击 | 能按文本**精准找到元素再点击** |

## 怎么正确拿控件树

直接查 WDA 的原生接口：

```bash
curl -s "http://127.0.0.1:18100/source?format=json"
```

返回当前前台 App 的完整元素树，含 `type`（StaticText/Button/Cell/Image…）、`label`、`frame`（坐标）。

## ⚠️ 关键坑：`name` vs `label`

**判断"App 是否有控件树"，不能用某些封装层的过滤结果。**

iPhone-use 的 `pua_observe mode:tree` 默认按元素的 **`name`** 字段提取。但 iOS 上**大多数 App 的可读文本在 `label` 字段，`name` 是 null**。于是 `pua_observe` 会返回空数组，**误报为"该 App 无控件树"**。

实测（用 `/source?format=json` 按 `label` 统计）：

| App | label 节点数 |
|---|---|
| 抖音 | 74 |
| 微博 | 74 |
| B站 | 70 |
| 知乎 | 69 |
| 集换社 | 43 |
| 微信 | 43 |
| 小红书 | 38 |
| 淘宝 | 18 |

**结论：主流 App 全都有丰富的控件树。** 场景脚本应当：
1. **首选**直接解析 `/source?format=json` 的 `label` 节点；
2. 或用 `pua_find`（它支持按 `label` 匹配）定位元素；
3. 仅在个别 App 真的无控件树时，才退化为截图 + 视觉模型。

## 控件树能拿什么、不能拿什么

- **能**：所有文字（标题、作者、数字、按钮、输入框）、元素类型、屏幕坐标、可点击性。
- **不能**：图片/视频内容本身、纯图形化的布局语义（比如"这个封面长什么样"）。

所以实际是**控件树为主、截图为辅**：控件树负责结构和文字，截图负责视觉校验和图片内容。
